# Configuration

This page is the reference for Ark Stack's configuration: how settings reach each process, every environment variable grouped by area with its default, purpose and the services that read it, the secrets the installer generates, and the values that must never change after installation.

## How configuration is read

The repository-root `.env` supplies the main settings. Compose overrides can supply additional service settings. `.env.example` documents the development defaults. On a host, the installer creates and maintains `.env` with mode `0600`.

Settings reach processes in three ways:

- **mise tasks.** `mise run dev`, `dev:server`, `dev:web`, `start`, `db:migrate`, `db:generate`, `db:studio`, `recover` and `host:install` load `.env` into the task's environment, overriding variables already set in your shell. Tasks that run `bun --env-file=.env …` (for example `test`, `maintain`, `edge:rejoin`, `recover:mfa`, `import`) load it too, but there the shell wins: Bun does not override variables that are already set.
- **Containers.** Compose substitutes `${VAR}` in `infra/platform/docker-compose.yml` from the environment of the `docker compose` command. Automatic `.env` discovery depends on the working and project directories, so the installer passes the checkout-root file explicitly. Exported shell variables take precedence over values in that file. Use the same explicit selection when running Compose by hand: `docker compose --env-file .env -f infra/platform/docker-compose.yml …`. `${VAR:?generated by installer}` means the variable is required; `${VAR:-x}` gives a default.
- **Per service.** Each container receives only the variables listed in its own `environment:` block. Many container settings are fixed in the Compose file (paths such as `/var/lib/ark/certs`, internal URLs such as `http://api:3000`), so the same name in `.env` (for example `ARK_CERT_DIR=./tmp/certs`) affects only processes run on the host: local development, the installer and scripts.

After changing a value, recreate the services that read it, for example:

```sh
docker compose --env-file .env -f infra/platform/docker-compose.yml up -d api domain-worker
```

The API checks its generated secrets at startup and rejects empty required values or supplied examples (`change-me…`, `dev-…-token`). `ARK_EDGE_GATE_TOKEN` and `ARK_EDGE_WATCHDOG_TOKEN` may be empty, but not an example value. An API process that receives `ARK_BACKUP_REQUIRED=1` also requires `ARK_BACKUP_EXECUTE=1`. Stock Compose sends those settings only to the backup worker. With separate workers, the API can start without the backup executor, repository, database provisioning and Stalwart secrets that belong to other services.

## Values that must never change

Some values are bound to data created at install time. Changing them does not re-encrypt or migrate that data.

| Variable                                                          | What breaks if it changes                                                                                                                                                       |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ARK_ROOT_KEY`, `ARK_ROOT_KEY_ID`                                 | Every sealed secret (database and client passwords, CA keys, provider and backup credentials) becomes unreadable. Restore these before any database restore.                    |
| `BETTER_AUTH_SECRET`                                              | Every session ends, and every enrolled TOTP secret and recovery code becomes unusable: each administrator needs an MFA reset with `mise run recover:mfa`.                       |
| `ARK_PLATFORM_PG_REPO_CIPHER_PASS`, `ARK_APP_PG_REPO_CIPHER_PASS` | The existing encrypted pgBackRest repositories, and the off-VPS copies made from them, can no longer be read. An off-VPS restore needs the original passes.                     |
| `ARK_CONTROL_DB_PASSWORD`, `ARK_APP_DB_PASSWORD`                  | PostgreSQL sets these owner passwords only when the data volume is first created. A new value no longer matches the role, and migrations or the database worker cannot connect. |

Values that can change with care:

- `ARK_API_DB_PASSWORD`: the installer re-applies the `ark_runtime` password on every run.
- `ARK_PGBOUNCER_ADMIN_PASSWORD`: the installer keeps PgBouncer's stored verifier in step with it.
- `ARK_EDGE_SNI_PORTS`: re-run the installer; it republishes the ports and recreates the edge namespace.
- Worker and agent tokens: change both sides together (the API and the worker) and recreate both. The installer never rotates them.
- `ARK_SETUP_TOKEN`: unused once the owner exists.

Copy `ARK_ROOT_KEY`, `ARK_ROOT_KEY_ID`, `ARK_MFA_RECOVERY_TOKEN`, both cipher passes and every backup target's restic password off the host.
