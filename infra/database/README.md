Application PostgreSQL is a separate cluster from the platform control database. Public traffic terminates on PgBouncer with `client_tls_sslmode=require`, explicit database/role admission, and no wildcard mapping. Privileged, backup, and bootstrap identities are denied on the public listener.

The `pgbouncer-public` Compose service runs `/usr/bin/pgbouncer` directly on the generated `/var/lib/ark/pgbouncer/pgbouncer.ini`; the image's own entrypoint, which builds a config from environment variables, is bypassed. It runs as uid 1000, the owner of Ark's mode-0600 config, userlist and TLS key, because every capability is dropped. `tests/security/pgbouncer-public.test.ts` enforces that shape and a PgBouncer version of at least 1.25.2 (CVE-2026-6664). `mise run test:pgbouncer` starts the service against a disposable `app-postgres` and connects over TLS with SCRAM as a runtime role.

On fresh installs, the installer uses the same generator with no database mappings and an empty userlist: TLS and SCRAM are required and no client or console administrator is admitted. Re-running the installer also replaces its exact legacy permissive placeholder, while preserving provisioned configurations. The smoke test exercises this bootstrap state before installing a runtime mapping. CI runs it with a host `psql` client (`postgresql-client` on Linux).

PgBouncer also joins a dedicated `database-loopback` bridge so Docker publishes `127.0.0.1:15432`, the host database-ingress relay target. Application PostgreSQL stays on the internal `database-management` bridge. The smoke test requires the loopback-only publication and logs in through that host port with verified TLS and SCRAM; a missing binding fails the check.

The smoke test defaults to port 15432, matching production. On a shared developer host where that port is busy, use `ARK_PGBOUNCER_SMOKE_PORT=0 mise run test:pgbouncer` to request a disposable loopback port (Compose 2.24.4+). The test still requires a loopback-only binding and verified TLS through the published host port.
